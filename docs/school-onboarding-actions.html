School Onboarding
Remediation

Branch sprint1_dev
Reviewed 15 Sep 2026
22 action items · 5 phases

The School Onboarding flow was built incrementally and never closed out. The admin screens work, but the feature around them is unfinished: the school itself is never onboarded, the subscription it is sold is never enforced or managed, and the credential emails the flow depends on are silently discarded. Below are the 22 items that close it, ordered so each phase unblocks the next.

Lead with this in the meeting

Three findings change the shape of the project rather than the size of the backlog. There is no school account — no login, no portal, no welcome email; onboarding today means an admin typed a name into a table. Nothing expires and nothing is enforced — the expiry job is commented out of the scheduler and no endpoint checks entitlement, so every school parent, child and teacher has permanent unlimited access. No payment is ever recorded, yet the Payment Management screen reports free school seats as revenue and will issue PDF receipts for them. Items 9, 15, 16 and 17 are the ones worth the client's time.

Add the missing schools columns

BlockerS · ~0.5d

The code reads and writes max_limit, subscription_type and email on schools, plus currency on subscriptions. No migration creates any of them — production has been hand-patched, so a fresh environment cannot create a school at all. Add a backfill-safe migration and an index on users.school_id.

02

Fix the quaterly enum typo

BlockerS · ~0.5d

Both school forms submit quarterly, but the column is enum('monthly','quaterly','yearly') — misspelled. Every quarterly school's subscription insert is rejected in strict mode or stored empty. Migrate the enum, update existing rows, and normalise the mixed-case status values at the same time.

03

Make emails actually send

BlockerM · ~2d

Imported parents and teachers receive nothing. The mail helper resolves templates from the database, falls back to a Blade view, and silently returns if neither exists — and only 2 of the 16 templates referenced in code exist. Since passwords are randomly generated and never shown in the UI, those accounts are unreachable.

This cannot be fixed from the panel: the "create template" screen is an empty stub, so admins can only edit templates that already have rows. Seed the missing templates, implement create/store, and make a missing template a visible failure instead of a silent one.

Finish the onboarding feature

This is the gap between what was specified and what exists
09

Create a school account and send the onboarding email

Largest gapL · ~5d

The school's contact email is collected, stored, and never used by any code path. The school is never given an account either — the user_id on the school record is the panel admin who created it. So after onboarding, a school has no login, no record of its own code, and no email telling it anything.

Create a school-contact account on a new column (keeping the existing one as the audit trail), send a confirmation carrying school name, code, plan, seat cap and login details, and add a resend action. Scope depends on decision A below.

SchoolController.php:398, 401 · every mail in the controller targets a student, teacher or deleted user
10

Make Add and Edit the same feature

HighM · ~2d

Add has no staff import, so onboarding a school with teachers is a forced two-step. Edit cannot change the contact email — it is neither validated nor written, so it can never be corrected after creation. And if both files are uploaded together, the staff file is silently dropped.

SchoolController.php:1042 early return · email omitted from update at :899–904
11

Unify the import into one service with real error reporting

HighL · ~4d

Student import is implemented twice with different duplicate rules, and error handling is inconsistent — bad rows are silently skipped, rows over the seat cap are silently discarded, and the admin is shown only a success count. Staff import aborts the whole file on some errors and silently skips others. There is no seat cap on staff at all.

Extract one import service with one rule set, wrap it in a transaction, return a per-row report, and dispatch the queued mail job that already exists but is never called — today the loop makes one blocking SMTP call per row.

SchoolController.php:405–530 and 909–1040 duplicated · SendStudentSignupMail.php never dispatched
12

Complete the activation lifecycle

HighM · ~2d

Deactivating a school cascades inactive to every one of its users. Reactivating it restores nothing — the reverse branch was never written. Imported users are also never given a status at all, relying on the column default.

Subscriptions, teacher profiles, quiz attempts and mood records are left orphaned, and there is no transaction. Add soft deletes, change the cascade, and clean up references.

P3

Revenue & entitlement

The commercial model does not currently exist in the system
14

Introduce a plans table and attribute subscriptions to schools

CriticalM · ~3d

There is no pricing model. Three hardcoded price literals are duplicated across three files, so a price change is a code deploy in three places. More importantly, subscriptions have no school reference — a subscription granted because of a school is indistinguishable from a consumer purchase, so per-school revenue is not computable at all.

Add a plans table, point schools at it, and add school, plan and a source flag to subscriptions so grants can be separated from purchases.

RegisterService.php:100–121 · SchoolController.php:505–515, 1013–1026 — identical literals
15

Build subscription lifecycle management

CriticalL · ~5d

Nothing expires. The expiry command exists and works, but its scheduler line is commented out — the only commented line among seven live ones. A one-month school grant is permanent access in practice.

There is also no school-level subscription — only one row per imported user. So changing a school's plan updates the school record but touches no existing subscription: already-imported users keep the old plan and price forever, and users imported later get the new one. Deactivating or deleting a school cancels nothing.

Add a school subscription record as the single source of truth, derive user entitlements from it, re-enable the expiry job, and cascade cancellation on deactivate and delete.

Kernel.php:28 — // $schedule->command('subscriptions:expire')->daily();
16

Record payments — and stop reporting grants as revenue

CriticalL · ~4d

School seats are written as successful paid subscriptions with a hardcoded price and no payment method, transaction, receipt, invoice or money collected. The receipt and transaction columns exist — for app-store purchases — and are left null.

Payment Management then lists every one of those free seats at its hardcoded price, with no school column and no way to tell a grant from a purchase, and offers a downloadable PDF receipt for a payment that never happened. Any revenue total from that screen is wrong by the entire school population.

Add a payments/invoices table, exclude grants from revenue totals, add school as a column and filter, and fix four defects in the receipt generator: a null dereference before its own guard, an undefined expiry variable for exactly the quarterly spelling schools use, expiry recomputed from the start date instead of the stored value, and an unvalidated date-range filter.

PaymentManagementController.php:186–198 · routes/web.php:325–328
17

Enforce entitlement on the server

CriticalL · ~4d

No endpoint anywhere checks whether a subscription is active. The only middleware on the authenticated API checks account and school status and nothing else; the subscription is read in one place, for display only. Everything else is commented out.

So entitlement is enforced client-side at best, which any direct API call bypasses. School parents have permanent access, children have no subscription of their own, and teachers are given no entitlement record at all yet have full access. Until this lands, items 14–16 grant and withhold nothing.

ApiCheckStatus.php · ChildController.php:600–612 display only; :332, 453, 590, 1034 commented out
18

Build the school email set and expiry notices

HighM · ~3d

There is no pre-expiry warning of any kind — no command, job or template. Around 14 emails this flow needs have no call site at all: onboarding confirmation and resend, import summary, seat limit reached, subscription activated, expiring at 30 / 7 / 1 days, expired, renewed, plan changed, payment receipt, deactivation and reactivation, plus welcome and access-revoked notices for parents and teachers.

One change to fold in here: the existing credential emails are designed to send a plaintext generated password. Replace that with a single-use expiring set-password link — it removes the plaintext exposure and the weak password generator together.

Depends on item 03 (templates deliverable) and item 15 (expiry actually runs)

Bring to the client

Four decisions that change the estimate

These are product questions, not engineering ones. Each materially changes the scope of the item it sits under, so getting answers in this meeting is worth more than any of the detail above.

A · What is a "school account"?

Does a school only need to receive email, or does it log into a real portal to see its students, seats and invoices?

Sets item 09 between roughly 2 days and several weeks.

B · How are seats priced?

Per seat against the school's limit, or a flat contract price per term regardless of headcount?

Determines the shape of the plans table in item 14.

C · How are schools billed?

An offline ledger an admin records payments into, or a real payment flow through a gateway?

Item 16 is either a simple table or a full integration.

D · What do teachers get?

Teachers currently have no entitlement record and unlimited access. Is that intended, or should they draw on the school's seats?

Item 17 cannot be specified without this.
